# 跨公司 SaaS 卡密分发 + 多租户客户端自动同步系统 — 完整规划

先明确一个关键点：你描述的"发卡端"和"用户端"是两个独立 APP，中间隔着不同公司的 SaaS 系统。这类系统的核心难点**不在发卡本身**，而在于**卡密作为"跨系统凭证"如何被安全地兑换、绑定、并在两端产生可对账的消费流水**。下面按你要的五个维度展开。

---

## 一、价值评估

### 1.1 场景定义（先锁死边界）
- **发卡端 SaaS**：A 公司（发卡方）在其 SaaS 后台批量生成卡密（兑换码 / License / 代金券），背后对应一定权益额度。
- **用户端 APP**：C 用户安装的客户端，支持多账号（多用户）登录。
- **中间**：卡密需要被"接收→兑换→绑定到某个用户/设备→产生消费记录"。
- **同步**：两端的消费记录要自动同步并互相确认（对账）。

### 1.2 价值主张
| 对象 | 价值 |
|---|---|
| 发卡公司 | 渠道分发、预付费回款、跨平台拉新 |
| 收单/使用方 | 无需自建支付体系即可承接权益 |
| 终端用户 | 一码通兑、多设备多账号统一资产 |
| 平台方（你） | 抽成 / SaaS 订阅 / 交易手续费 |

### 1.3 商业模式
1. **SaaS 订阅制**：发卡方按年付费用发卡后台。
2. **交易抽佣**：每笔卡兑换抽 1%~5%。
3. **API 调用计费**：按同步/对账请求量阶梯定价。
4. **白标私有化部署**：大客户一次性 + 年维护。

### 1.4 关键风险
- 卡密被撞库 / 盗刷 → 必须一次性核销 + 幂等。
- 两端账本不一致 → 必须**最终一致 + 对账兜底**，不能只靠"实时"。
- 跨公司信任问题 → 需要中间可信方或区块链式存证。
- 合规：虚拟资产、预付卡在部分地区受监管（需咨询当地法务）。

## 二、产品需求（PRD 概要）

### 2.1 角色
- **发卡方管理员**：生成卡批次、设置额度/有效期/适用商品、查看核销报表。
- **用户端多用户**：主账号 + 子账号，共享或独立资产。
- **平台运营**：处理对账差异、风控封禁。

### 2.2 核心功能需求

**发卡端**
- FR-1 批量生成卡密（加密随机、防枚举）
- FR-2 卡属性：面额、有效期、绑定上限、可转让性
- FR-3 批次管理与导出（CSV/API 下发到渠道）
- FR-4 核销回调接收与状态更新

**用户端**
- FR-5 多用户体系（主/子账号、权限）
- FR-6 卡密录入（扫码/手动/深链）
- FR-7 本地资产账本（离线可读）
- FR-8 消费动作触发（消费即上报）
- FR-9 同步状态可视化（已同步/待确认/冲突）

**同步与对账**
- FR-10 实时/定时双向同步
- FR-11 消费确认机制（三方确认：发卡方账、用户端账、平台账）
- FR-12 冲突解决策略（以服务端账本为准 + 时间戳/序号）
- FR-13 对账报表与差异告警

### 2.3 非功能需求
- 幂等：同一卡密重复提交只核销一次。
- 最终一致：网络中断后可补同步。
- 安全：卡密端到端加密、防重放。
- 性能：同步延迟 < 2s（实时通道），对账批量 T+0/T+1。

## 三、产品设计（架构与交互）

### 3.1 整体架构

```
┌─────────────┐        ┌──────────────────┐        ┌─────────────┐
│ 发卡端 SaaS  │◄──API──►│  中间平台(你)      │◄──API──►│ 用户端 APP   │
│ (A公司)      │        │  - 卡密中心        │        │ (多用户)     │
└─────────────┘        │  - 账

┌─────────────┐        ┌────────────────────┐        ┌──────────────┐
│ 发卡端 SaaS  │◄──API──►│   中间平台（你）     │◄──API──►│  用户端 APP   │
│  (A 公司)    │        │  - 卡密中心         │        │  (多用户)     │
└─────────────┘        │  - 统一账本         │        └──────────────┘
                       │  - 同步/对账引擎     │               │
                       │  - 风控/审计         │        ┌──────┴───────┐
                       │  - 消息网关          │        │ 本地 SQLite/   │
                       └─────────┬──────────┘        │ 加密账本       │
                                 │                    └──────────────┘
                    ┌────────────┴────────────┐
                    │  MQ(Kafka) + Redis      │
                    │  + 对象存储 + 数仓       │
                    └─────────────────────────┘
```

**核心设计原则**：中间平台不是"转发器"，而是**唯一的真相源（Single Source of Truth）**。两端本地账本都视为"缓存 + 待确认队列"，所有冲突以平台账本 + 序号为准。

### 3.2 卡密生命周期（状态机）

```
CREATED → ISSUED → REDEEMED(锁定) → BOUND(绑定用户) → ACTIVE
                                        │
                          CONSUMED ─────┼───── EXPIRED
                                        │
                                     REFUNDED
```

- **REDEEMED 与 BOUND 分离**：兑换（核销卡密）与绑定（归属某用户）分两步，便于"先锁后绑"，防止并发重复核销。
- 每张卡带 `card_id + nonce + 面额 + 签名`，卡密本身 = 随机串 + HMAC 签名，防伪造。

### 3.3 用户端多用户模型

```
主账号 (OwnerAccount)
 ├── 子账号 A（独立资产）
 ├── 子账号 B（共享资产池）
 └── 设备列表（Device 1..n，每设备有 device_id + 公钥）
```
- 资产归属：**卡绑到"账号"而非"设备"**，设备只是登录载体，避免换机丢资产。
- 多用户并发消费 → 用**乐观锁 + 版本号（version）** 解决。

## 四、产品技术（实现方案）

### 4.1 两端需要做什么"增强"

**服务器端（平台侧）**
1. **统一账本服务（Ledger Service）**
   - 采用**复式记账**：每笔消费生成 `debit/credit` 两条分录，可对账。
   - 每笔交易带全局单调递增 `seq`，作为同步序号基准。
2. **同步引擎**
   - 实时：WebSocket / MQTT 长连接推送变更（增量）。
   - 定时：客户端轮询 `GET /changes?since=seq`（补偿拉取）。
   - 幂等表：`idempotency_key` 唯一索引，防重复消费。
3. **对账引擎**：定时比对三方流水（发卡方回调、平台账本、用户端上报），产出差异单。
4. **风控**：卡密撞库检测（同一 IP 高频失败）、异常消费速率、设备指纹。
5. **消息网关**：统一 push（APNs/FCM/厂商推送 + WebSocket 兜底）。

**个人端（用户端 APP）**
1. **本地加密数据库**（SQLite + SQLCipher），存本地账本 + 离线队列。
2. **离线优先**：无网也能"记账"，联网后补同步（CRDT 思路或纯 LWW + seq 覆盖）。
3. **设备密钥对**：每设备生成密钥，请求签名，防重放。
4. **同步状态机 UI**：待同步/同步中/已确认/冲突，给用户可见反馈。
5. **深链/扫码收卡**：`app://redeem?code=xxx`。

### 4.2 同步与确认协议（关键技术）

**实时同步流程**
```
1. 用户端扫码 → 本地校验格式 → 生成 redeem 请求(key=UUID)
2. 平台校验卡状态 → 加分布式锁(Redis SETNX card_id) → 置 REDEEMED
3. 平台写账本(seq=N) → 返回 {card_id, balance, seq}
4. 平台通过 WS 推给该用户所有设备 → 各设备更新本地账本
5. 各设备回 ACK → 平台标记"已确认设备集合"
```

**消费确认（三阶段）**
1. **发起**：用户端本地扣减（乐观）+ 上报 `spend` 事件。
2. **平台确认**：平台账本记账，返回 `seq` + 签名回执。
3. **双向确认**：发卡方异步回调确认 → 平台标记 FINAL → 推送用户端"已对账"。

**冲突解决规则（优先级从高到低）**
1. 平台账本为准；
2. 同源用高 `seq` 覆盖低 `seq`；
3. 余额不可为负，冲突则回滚本地并拉全量。

### 4.3 通信协议选型

| 需求 | 方案 | 理由 |
|---|---|---|
| 实时推送 | WebSocket + MQTT | 双向、低延迟、移动端省电 |
| 离线补拉 | REST 增量 API | 简单、可缓存 |
| 跨公司对接 | HTTPS + Webhook + 签名 | 标准化、易审计 |
| 高可靠事件 | Kafka | 削峰、可重放、可追溯 |
| 内部缓存/锁 | Redis | 幂等、分布式锁 |

### 4.4 安全设计
- 卡密：`HMAC-SHA256(card_payload, secret)`，密文存储，仅哈希入库。
- 传输：TLS 1.3，请求签名 + 时间戳 + nonce 防重放。
- 权限：OAuth2 / JWT，多租户数据隔离（tenant_id 强制过滤）。
- 审计：所有状态变更写不可篡改日志（append-only + 定期校验和）。

### 4.5 数据模型（核心表）
```sql
card(card_id, batch_id, tenant_id, amount, status, expire_at, hmac)
card_binding(card_id, account_id, bound_at)
ledger_entry(entry_id, account_id, card_id, seq, debit, credit, type, ts)
spend_event(event_id, idempotency_key, account_id, amount, status, seq)
sync_cursor(device_id, last_seq)
recon_diff(diff_id, source, expected, actual, status)
```

## 五、产品验证

### 5.1 验证目标
| 目标 | 指标 | 达标线 |
|---|---|---|
| 同步正确性 | 三方账本一致率 | ≥ 99.99% |
| 实时性 | P95 同步延迟 | < 2s |
| 幂等性 | 重复请求产生重复扣款 | = 0 |
| 并发安全 | 同卡并发兑换成功率 | 100% 单次核销 |
| 离线恢复 | 断网 24h 后补同步成功率 | ≥ 99.9% |
| 对账 | T+1 差异单占比 | < 0.01% |

### 5.2 测试方案
1. **单元/集成测试**：状态机、幂等、账本分录。
2. **并发压测**：万级并发抢同一张卡，验证分布式锁 + 幂等。
3. **混沌工程**：断网、丢包、时钟漂移、MQ 延迟，验证最终一致。
4. **端到端**：发卡方生成 → 渠道下发 → 用户端兑换 → 消费 → 对账闭环。
5. **安全测试**：撞库、重放、越权、篡改请求签名。
6. **灰度发布**：先小批量卡批次 + 少量用户端版本，观察差异率。

### 5.3 验证里程碑
- **M1 概念验证（POC）**：单张卡全链路打通，2 端能收发。
- **M2 一致性验证**：1000 张卡 + 1000 用户，测对账一致率。
- **M3 压力与混沌**：并发 + 故障注入。
- **M4 试点**：1 家发卡公司 + 100 真实用户灰度。
- **M5 规模化**：多租户 + 白标。

## 七、最容易踩的坑（务必注意）

1. **别把"实时"当唯一手段**——网络不可靠，必须有定时补拉 + 对账兜底，否则账本必错。
2. **卡密核销必须分布式锁 + 幂等键双保险**，单靠数据库唯一索引在跨库场景会漏。
3. **卡绑账号而非设备**，否则用户换机/多设备会丢资产或重复领取。
4. **多用户并发消费**必须版本号或乐观锁，否则余额超扣。
5. **跨公司信任**：发卡方回调可能失败/伪造，需回调签名 + 主动对账双验证。
6. **合规先行**：预付卡/虚拟资产在部分地区需牌照，尽早确认。

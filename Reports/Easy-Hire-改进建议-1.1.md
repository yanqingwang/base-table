# Easy Hire 深度分析 & 改进建议 v1.1 — 面向一线工人招聘的规划设计

**报告日期**: 2026年7月4日  
**测试范围**: 后端 64 项集成测试 + 全代码架构审查 + 数据库 Schema 分析 + 前端 28 文件审查 + 业务逻辑审计  
**分析视角**: 面向**一线工人招聘 (Blue-Collar Recruitment)** 场景的重新规划设计

---

## 执行摘要

v1.0 完成了 API 认证、错误处理、前端代码拆分、测试覆盖等 **P0/P1 修复**。  
v1.1 在此基础上做**深度架构审计 + 面向一线工人招聘场景的重新规划设计**。

核心发现：当前系统是从 "白领招聘管理系统" 角度构建的——候选人 38 个字段、13 个状态、长表单。  
面向一线工人招聘，需要**大幅简化**：手机号优先、批量操作、叫号系统为核心、移动端优先、多语言。

## 1. 🏗️ 架构分析 — 面向一线工人招聘的重新设计

### 当前架构问题

| # | 问题 | 位置 | 当前影响 | 一线工人场景影响 |
|---|------|------|----------|------------------|
| 1 | **God File** — `lib.rs` 1528 行，`db.rs` 2837 行 | 两个文件占代码库 84% | 可维护性差 | 批量操作如 CSV 导入、批量创建候选人需要跨模块协作，更难维护 |
| 2 | **无 Service Layer** — Handler 直接调 `db.*` | `lib.rs` 全部 handler | 业务逻辑和 HTTP 层混合 | 队列叫号/批量入职等复杂流程无法复用 |
| 3 | **无连接池** — 每次请求新 SQLite 连接 | `db.rs:403-405` | 性能差 | 高峰期数百名工人同时面试 → 连接风暴 |
| 4 | **硬编码配置** — 端口/CORS/JWT 过期时间 | 多文件 | 部署不灵活 | 多站点部署时需要改代码 |
| 5 | **CORS 硬编码 localhost:5174** | `lib.rs:224` | 无法在生产环境使用 | 面试现场用平板访问 → 跨域失败 |
| 6 | **字符串匹配错误码** — `E(String)` | `error.rs:18-26` | "not found" 关键词误触 404 | 错误信息暴露给工人不友好 |

### 🔑 需要讨论的设计决策

> **Q1**: 是否需要 Service Layer？当前 Handler → DB 直调对简单 CRUD 够用，但叫号/批量入职等流程需要编排。  
> **选项 A**: 保持扁平，在 handler 中编排（简单但重复）  
> **选项 B**: 添加薄 Service Layer 编排复杂流程（推荐）  
> **选项 C**: 部分抽取——叫号/批量操作抽 Service，CRUD 保持直调（中庸）

> **Q2**: 是否引入连接池 (r2d2-sqlite / deadpool-sqlite)？  
> **选项 A**: 保持单连接/WAL 模式（简单，够用）  
> **选项 B**: 引入连接池（推荐，面试高峰期 50+ 并发请求）

## 2. 🗄️ 数据库分析 — 26 张表的深度审计

### 严重问题

| 严重度 | 问题 | 位置 | 说明 |
|--------|------|------|------|
| 🔴 **Critical** | **PRAGMA foreign_keys=ON 从未设置** | 全局 | 所有 24 个 FK 声明形同虚设。SQLite 默认 FK 强制关闭。孤儿记录必然存在 |
| 🔴 **Critical** | **SQL 注入漏洞** | `db.rs:931-937` | `candidate_by_phone_or_email` 使用字符串拼接而非参数化查询 |
| 🔴 **Critical** | **零事务** | 全局 | 无 BEGIN/COMMIT。`transfer_approval`(3条语句)、`create_evaluation`(DELETE+INSERT) 都有部分写入风险 |
| 🔴 **Critical** | **每次方法调用新连接** | `db.rs:403-405` | `conn()` 每次打开新 SQLite 连接。无 WAL 模式、无 busy_timeout、无连接池 |
| 🔴 **Critical** | **零索引** | 全局 | 无 CREATE INDEX。`status`、`candidate_id`、`job_id` 查询全部全表扫描 |

### 中等问题

| # | 问题 | 说明 |
|---|------|------|
| 6 | `candidates.email` 和 `phone` 无 UNIQUE | 仅 CSV 导入时代码检查，API 可插入重复 |
| 7 | v2.0 字段无 FK 约束 | `jobs.department_id` 等无参照完整性 |
| 8 | 38 列 SELECT 列表重复 9 次 | 加字段需改 9+ 处 |
| 9 | JSON 存 TEXT 字段 | skills/skill_scores/ocr_data 无法 SQL 查询 |
| 10 | 面试核心表无 ON DELETE CASCADE | 删面试后遗留孤儿 round/assignment/evaluation |

### 26 张表索引缺失清单

| 表 | 需要的索引 | 为什么 |
|----|-----------|--------|
| `candidates` | `(phone)`, `(status, source)`, `(agency_id)` | 手机号查询（工人报名）、状态过滤、中介查询 |
| `interviews` | `(candidate_id)`, `(job_id)`, `(status)` | 按候选人/职位/状态查询 |
| `interview_queue` | `(job_id, status)`, `(candidate_id)` | 叫号核心查询、重复入队检查 |
| `approvals` | `(assigned_to, status)`, `(candidate_id)` | 审批人待办、候选人审批历史 |
| `job_applications` | `(job_id)`, `(candidate_id)` | 职位申请数、候选人申请历史 |
| `audit_logs` | `(entity_id, entity_type)` | 审计追踪 |

### 面向一线工人的 Schema 简化建议

当前 `candidates` 表 38 个字段，大部分对一线工人不必要。

**建议简化候选人为两类**：

```
# 快速登记（工人报名/中介批量导入）
phone (PRIMARY KEY or UNIQUE)
name
id_number
country_code (国籍/工作地)
agency_id
source (direct / agency / referral)
status
created_at

# 详细信息（入职前补充）
→ 通过 sub-tables 按需扩展：addresses, bank_accounts, family_members, documents
→ 教育/工作经历对一线工人不再需要独立子表
```

### 🔑 需要讨论的设计决策

> **Q3**: 13 个候选人状态是否简化？  
> 当前：new→screening→queue_waiting→interviewing→evaluated→offered→document_signing→signed→pre_onboarding→ready_to_sync→synced→hired→rejected  
> 建议简化：applied→screened→interviewed→offered→hired→rejected (+ withdrawn)  
> 但 8 个状态无代码触发，建议先清理不可达状态再决定

> **Q4**: 手机号作为工人唯一标识？  
> 一线工人经常无邮箱、高频换号、一人多次报名。手机号去重还是允许一号码多记录？

## 3. ⚙️ 业务逻辑分析 — 竞态条件 & 状态机

### 竞态条件（无锁并发）

| # | 位置 | 问题 | 严重度 | 一线工人场景影响 |
|---|------|------|--------|-----------------|
| 1 | `db.rs:2407-2435` | **call_next()** — SELECT + UPDATE 无事务，两个叫号员同时叫到同一个人 | 🔴 Critical | 面试大厅两个窗口同时叫同一个人 |
| 2 | `db.rs:2376-2405` | **enqueue** — SELECT MAX + INSERT 无事务，相同 queue_number | 🔴 Critical | 两个工人拿到同一个排队号 |
| 3 | `lib.rs:795-833` | **create_employee** — 检查 status=="offered" 再 INSERT，两个并发同时过检查 | 🟡 Medium | 重复入职（但 UNIQUE 约束会阻止） |
| 4 | `db.rs:1410-1445` | **transfer_approval** — 原审批已处理后仍可转交 | 🟡 Medium | 已批/已拒的审批还能产转子审批 |

### 状态机问题

| # | 问题 | 影响 |
|---|------|------|
| 1 | **13 个状态中 8 个不可达** | `queue_waiting`、`interviewing`、`evaluated`、`document_signing`、`signed`、`pre_onboarding`、`ready_to_sync`、`synced` 无代码触发 |
| 2 | **状态转换无校验** | `update_candidate` 接受任意状态字符串，不验证合法性 |
| 3 | **两条路径设置 "offered"** | 面试通过和审批通过都设置 offered，无区分 |
| 4 | **拒绝不更新候选人状态** | 审批拒绝后候选人仍留在 "offered" |
| 5 | **入队不更新候选人状态** | `enqueue_candidate` 不设置 candidate.status = 'queue_waiting' |
| 6 | **面试完成不更新候选人状态** | 面试结束（evaluate）直接设 "offered"（如果 pass），跳过了 "interviewing" 和 "evaluated" |

### 权限漏洞

| # | 端点 | 问题 | 一线工人场景影响 |
|---|------|------|-----------------|
| 1 | `PUT /interviews/:id/checkin` | 任意登录用户可 checkin 任意面试 | 工人可以给自己 checkin — 实际上是需要的功能！ |
| 2 | `POST /documents/:id/sign` | 任意登录用户可签署文档 | 安全风险 |
| 3 | `GET /candidates` | 任意用户可查看全部候选人 | 中介不能看其他中介的候选人 |
| 4 | `GET /employees` | 任意用户可查看全部员工 | 严重隐私泄露 |

### 面向一线工人的业务逻辑建议

**叫号流程（核心）**：
```
工人报名 → 入队(waiting) → 叫号(called) → 面试中(in_progress) 
→ 通过 → offered → 签署 → hired
→ 不通过 → rejected
```

**简化后的状态机**：
```
status: applied | screened | interviewed | offered | hired | rejected | withdrawn

合法转换:
applied → screened (筛选通过)
screened → interviewed (安排面试)
interviewed → offered (面试通过)
interviewed → rejected (面试不通过)
offered → hired (确认入职)
offered → rejected (放弃入职)
hired → withdrawn (离职)
```

### 🔑 需要讨论的设计决策

> **Q5**: 叫号竞态条件如何修复？  
> **A**: SQLite 事务包 SELECT + UPDATE（简单，够用）  
> **B**: 应用层分布式锁（过度设计）  
> **C**: 增加状态检查 WHERE status='waiting'（当前已有，但 SELECT+UPDATE 非原子）

> **Q6**: 权限模型简化？  
> 一线工人招聘的典型角色：admin（系统管理）、recruiter（招聘员/面试官）、manager（审批经理）、agency（中介）  
> 是否增加 `interviewer` 角色单独权限？还是 recruiter 兼面试官？

## 5. 👤 以用户为中心 — 三类用户场景设计

### 工人 (Worker) 体验

| 场景 | 当前 | 建议 |
|------|------|------|
| 报名 | 需要在电脑上填 38 个字段 | 手机打开 → 选职位 → 输入手机号+姓名 → 拿排队号 |
| 排队 | 无 | SMS/WhatsApp 通知 "您的号码是 A035，前面还有 12 人" |
| 面试 | 无指引 | 大屏显示 "A035 请到 3 号窗口" + 声音播报 |
| 结果 | 无 | SMS/WhatsApp 通知 "面试通过，请等待入职通知" |
| 入职 | 在线填表 | DocuSign 签名 + 上传身份证/银行卡照片 |

### 招聘员 (Recruiter) 体验

| 场景 | 当前 | 建议 |
|------|------|------|
| 叫号 | 缺少 Call Next 按钮 | 一键叫号 → 大屏显示 → 工人到来 → 完成/跳过 |
| 面试记录 | 需填评估表单 | 简单打分 (1-5) + 通过/不通过 |
| 批量操作 | 无 | 批量入队、批量标记状态 |
| 查询工人 | 搜索全部字段 | 手机号快速搜索 + 最近报名列表 |

### 中介 (Agency) 体验

| 场景 | 当前 | 建议 |
|------|------|------|
| 提交工人 | CSV 导入 | CSV 预览 + 去重提示 + 批量入队 |
| 追踪状态 | 无 | 看板：已提交/已面试/已录取/已入职 |
| 批量入职 | 逐个创建 | 一键批量创建员工 + 批量发送 DocuSign |
| 结算 | 无 | 按入职人数统计报表 |

### 管理者 (Manager) 体验

| 场景 | 当前 | 建议 |
|------|------|------|
| 审批 | ApprovalList 可用 | 保持 + 添加一键批量审批 |
| 报表 | Dashboard + Hiring Funnel | 添加：按职位/中介/日期维度的招聘漏斗 |
| 批量入职 | 无 | 批量审批 → 批量创建员工 → 批量 DocuSign |

## 三、经验教训（下次避免踩坑）
1. **先探明真实代码库再动手**：本轮差点把新实现当"原服务"盲迁；真相在 `code/card-counter-flask`，不是 wechat/。
2. **与既有代码并存先对齐约定**：表名/列名/ORM 风格不一致会产生重复表 → 采用"复用现有表 + 新增模块"，不要照搬平行实现。
3. **集成踩过的坑（均已修复，写测试时直接注意）**：
   - 响应信封 `{'code':0,'data':...}`（成功）/ `{'code':-1,'errorMsg':...}`（失败）→ 测试必须 unwrap `data`
   - 顾客侧 `require_auth` 没有 `current_merchant_id` → merchantId 从 query/body 取（`_mid()`）
   - 返回 `(result, idempotent)` 元组的服务函数，路由层必须取 `[0]`，否则被 JSON 序列化成 list
   - 直接调用 dao（如 `create_user`）需在 `app.app_context()` 内；ORM 对象跨 context 会 `DetachedInstanceError` → 测试整体包 context
   - 商户侧所有路由要带 `merchantId`（require_staff_auth 从 query/body 取）
4. **并发强一致演示依赖单进程**：后台服务与测试必须在同一 shell 会话（本沙箱跨 Bash 调用会回收后台进程）
5. **迁移用增量补列，不要 create_all 裸奔**：老库升级不丢数据的保证由 `migrate()` + 补列迁移块提供
6. **幂等设计**：核销用 `verify_token`（token 即幂等键），其余类资金操作（预约/销卡/退款）用 `idempotency_keys` 表

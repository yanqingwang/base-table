## 1. 执行摘要

本报告评估了三种将HR服务作为全球"产品目录"进行分类的方式（每种2–3层结构），并结合泰科电子（TE Connectivity）的实际情况给出定制建议：

| 场景 | 分类逻辑 | 一句话结论 |
|---|---|---|
| **场景1** 传统HR职能 | 薪酬、招聘、员工关系等专业条线 | HR视角合理，员工视角一般，适合做**后台服务主数据骨架** |
| **场景2** HR组织架构 | SSC / CoE / HRBP / 属地HR | 员工端**反模式**，仅可作为路由元数据 |
| **场景3** SSC服务模式 | 员工生命周期 + 关键时刻 + 分层交付 | 员工最直观，**推荐作为前台导航** |

### 核心建议：前后台解耦的双层分类体系（"3 + 1 + 组织架构作元数据"）

- **前台（员工/经理可见）** = 场景3：生命周期与角色导向的8个一级类目（"我的薪酬与时间"、"人生与工作事件"、"经理工作台"），用员工的语言，不用HR的语言
- **后台服务主数据** = 场景1：职能域作为每个服务项的唯一"户口"，挂接全球服务负责人、流程映射、SLA
- **组织架构（场景2）永不暴露给员工**，只作为路由属性存在——HR重组不影响员工体验
- **搜索优先，类目兜底**：搜索/AI入口是主路由，类目服务于浏览发现和完整性

### TE定制核心结论（详见第11节）

TE约八成员工为工厂一线人员，分布于约50个国家的生产基地，横跨三大事业部并伴随持续并购。因此：**一线员工（deskless worker）体验是TE分类体系成败的第一约束条件**，而非锦上添花；分类体系必须同时成为**并购整合加速器**（新收购公司=实例化全球模板+本地法定项）；德国劳资委员会、中国PIPL数据合规、墨西哥法定福利构成三大本地化深水区。

### 2.2 由此推导的六大设计约束

| # | 约束 | 对分类体系的直接影响 |
|---|---|---|
| C1 | **一线员工为主体** 🏭 | 移动端/车间自助机（kiosk）/扫码入口是主通道；一级类目须适配大图标瓦片式浏览；主管代提单（proxy request）为必备能力 |
| C2 | **考勤类需求量占主导** | 工厂人群的案例量中排班/加班/考勤/请假通常占40%以上 → "My Time 我的时间"在工厂角色视图中须置顶 |
| C3 | **多语言多文化** | 至少两级语言策略：T1全量本地化（英/简中/西/德），T2界面+高频知识本地化（捷克语、匈牙利语、日语等） |
| C4 | **三大事业部 + 站点维度** | BU是路由属性而非导航类目；**对一线人群，"工厂站点（Site）"比BU更重要的路由键** |
| C5 | **持续并购** | 分类体系须产品化、模板化，新公司接入=配置而非重建 |
| C6 | **劳资委员会与数据合规** | 德国案例可见性限制、协商前置步骤；中国PIPL员工数据出境评估；欧盟GDPR——影响L3设计、路由与知识可见性 |

## 3. 设计原则与维度

### 3.1 层级定义

| 层级 | 定义 | 经验法则 | 变更频率 |
|---|---|---|---|
| **L1 服务域** | 员工看到的顶层导航类目 | 最多6–9个（认知负荷上限），名称面向结果、长期稳定 | 3–5年稳定，须分类委员会批准 |
| **L2 服务组** | 域内相关服务的聚类 | 每个L1下4–8个，无HR行话 | 年度评审 |
| **L3 服务项** | 可实际发起的服务/工单类型，挂接负责人、SLA、受众与国家范围 | 动词/结果导向命名（"申请在职证明"），**本地化发生在这一层** | 持续，走治理化的准入流程 |

### 3.2 必须覆盖的维度

| 维度 | 设计含义 |
|---|---|
| **多地点** | L1/L2全球统一；L3带国家/区域可见性范围与本地化履约。如"福利登记"全球存在，但德国/中国/巴西呈现不同表单与知识 |
| **多事业部** | BU是范围与路由属性，不是导航类目。除非BU确有独特服务（如制造倒班服务 vs 总部服务） |
| **多层级员工** | 角色化视图：员工 / 经理 / 高管 / HR / 外包与派遣 / 候选人 / 校友 / 退休人员——同一分类体系，按角色过滤呈现 |
| **一线员工** 🏭 | kiosk/移动/扫码/企业微信-Teams入口、简化L1瓦片、主管代提单、工会与劳资委员会约束 |
| **语言** | 类目标签集中翻译；每种语言维护搜索同义词（工资单 / payslip / Gehaltsabrechnung / recibo de nómina） |

## 4. 场景1：按传统HR职能分类

**逻辑**：类目对应经典HR专业条线——HR专业人员的思维方式，也是多数流程架构（如APQC）与HCM系统模块的结构。

### 4.1 分类总览（9个L1）

| L1 服务域 | 图标 | L2 服务组 |
|---|---|---|
| 1. 招聘与入职 Talent Acquisition & Onboarding | 🧲 | 招聘与内部流动 / 入职前 / 入职与试用期 |
| 2. 薪酬与福利 Compensation & Benefits | 💰 | 薪酬 / 福利 / 认可与股权 |
| 3. 工资、考勤与休假 Payroll, Time & Absence | ⏱ | 工资 / 考勤 / 休假 |
| 4. 学习与发展 Learning & Development | 📚 | 培训与合规学习 / 领导力与职业发展 / 教育资助与认证 |
| 5. 绩效与人才管理 Performance & Talent | 🎯 | 目标与绩效评估 / 人才盘点与继任 / 晋升与岗位变动 |
| 6. 员工关系与合规 ER & Compliance | ⚖️ | 职场诉求 🔒 / 纪律与调查 🔒 / 政策解读与劳资关系 |
| 7. 人事行政与数据 HR Administration | 📄 | 个人数据变更 / 证明信与验证 / 合同与文档 |
| 8. 全球流动 Global Mobility | ✈️ | 国际派遣与搬迁 / 移民与工作许可 |
| 9. 离职与退休 Offboarding & Retirement | 🚪 | 辞职与离职流程 / 退休规划 / 校友与返聘 |

### 4.2 L3示例（节选）

- **3. 工资、考勤与休假** ⏱
  - 工资 Payroll
    - 工资单查询/差异申诉 · 个税表单/证明申请 📍 · 银行账户变更
  - 考勤 Time & Attendance 🏭
    - 考勤记录更正 🏭 · 加班/换班申请 🏭（制造关键项）
  - 休假 Absence & Leave
    - 年假查询 · 育儿/产假案例 📍 · 病假与医疗证明提交 📍
- **6. 员工关系与合规** ⚖️
  - 职场诉求与申诉 🔒（保密案例处理）
  - 纪律与调查 👔🔒（经理/HR发起）
  - 政策解读与劳资委员会事务 📍（德国等）

### 4.3 优劣势

| ✔ 优势 | ✘ 劣势 |
|---|---|
| 与流程架构、CoE归属1:1对应 → 治理最简单、服务负责人最清晰 | 员工须先知道"哪个职能管我的问题"——"我结婚了"涉及福利+工资+休假+人事行政4个类目 |
| 与ServiceNow HRSD的COE结构、HCM模块天然对齐 | 跨职能人生事件（搬迁、生育、晋升）被切碎 |
| 职能稳定，HR重组不影响分类 | 类目名易陷入HR行话（"Total Rewards"） |
| 流程-服务映射（SC-007）最容易 | 经理任务散落各处，经理体验差 |

## 5. 场景2：按HR组织架构分类

**逻辑**：类目对应HR组织的实际结构（Ulrich三支柱）：CoE、HRBP、共享服务中心、属地HR。

### 5.1 分类总览（🔧 统一标识为"内部路由视图"）

| L1 | L2 | L3示例 |
|---|---|---|
| 1. HR共享服务中心 HRSSC | 一线服务台 Tier-1 | 通用HR咨询 · 门户使用帮助 |
| | 工资运营团队 | 工资差异工单 · 个税证明开具 📍 |
| | 人事事务团队 | 数据变更处理 · 在职证明开具 |
| | 入/离职运营团队 | 入职材料处理 · 离职结算 |
| 2. 专业中心 CoE | 整体薪酬CoE | 薪酬对标请求 👔 · 福利方案设计升级 |
| | 招聘CoE / 人才与学习CoE / 员工关系CoE 🔒 / 全球流动CoE | …… |
| 3. 业务伙伴 HRBP | 各Segment/BU HRBP团队 | 组织设计咨询 👔 · 人力规划支持 👔 |
| 4. 属地HR Local HR | 国家HR运营 📍 | 法定申报、本地福利 |
| | 工厂现场HR 🏭 | 倒班问题、劳资委员会/工会事务 |
| 5. HR技术与分析 HRIT | 系统支持 / 报表与数据请求 | …… |

### 5.2 ⚠️ 员工端反模式警告

> **康威定律问题**：目录会"出厂即附带你的组织架构图"。员工不应需要知道工资组在SSC还是财务、福利归哪个CoE。
>
> - **脆弱**：每次HR重组都会打破导航，让数万员工重新学习，书签和肌肉记忆全部失效
> - **全球不一致**：同一服务在A区由SSC交付、在B区由属地HR交付——组织架构型分类无法呈现统一全球目录（直接冲突SC-017/SC-020）
>
> **合理用途**：作为**后台路由与派单组模型**（谁来履约），以及HR内部目录（HR-to-HR请求，如HRBP向CoE申请对标数据）。它应作为每个L3背后的元数据存在——**永不作为前台导航**。

## 6. 场景3：按HR共享服务（SSC）模式分类

**逻辑**：按共享服务组织"产品化"服务的方式设计——**前台**类目跟随员工生命周期与"关键时刻"（moments that matter），用员工自己的语言表达；**交付**按服务分层组织（Tier 0自助 → Tier 1通才 → Tier 2专家 → Tier 3 CoE/HRBP）。这是成熟ServiceNow HRSD实施的收敛模式。

### 6.1 前台分类（员工/经理视角，8个L1）

#### 🪪 L1-1. 我的信息 Me & My Information
- 个人信息（姓名、住址、紧急联系人、家属）
- 证明与文档（在职证明、签证函、合同副本）
- 我的HR记录与数据隐私请求 📍（GDPR/PIPL）

#### 💵 L1-2. 薪酬与时间 Pay, Time & Money
- 我的工资（工资单、扣款、银行账户、个税 📍）
- 我的时间 🏭（考勤、加班、换班——工厂角色视图置顶）
- 休假 Time Off（年假、病假、育儿假 📍、长假）
- 报销与津贴 📍

#### 🏥 L1-3. 健康、福利与关怀 Health, Benefits & Wellbeing
- 我的福利（登记、变更、理赔、保险）📍
- 身心健康支持（EAP、心理健康、人体工学）
- 退休与储蓄计划 📍

#### 🚀 L1-4. 职业、学习与绩效 My Career, Learning & Performance
- 学习与培训 · 绩效与目标 · 职业发展与内部机会 · 认可与反馈

#### 🌱 L1-5. 人生与工作事件 Life & Work Events（跨职能旅程）
- 我要入职 I'm Joining（打包：招聘+IT+工资+福利开通）
- 家庭变化 Family Changes（结婚、生育 → 打包：休假+福利+个税+数据变更）📍
- 我要调动/搬迁（内部调动、国际流动、移民 📍）
- 我要离职/退休（离职旅程、最终结算、校友）

#### 🏢 L1-6. 工作场所与制度 Workplace & Policies
- 政策与制度指南（知识为主，Tier 0优先）
- 提出诉求 Raise a Concern 🔒（申诉、伦理、骚扰——保密路由）
- 工作健康与安全 🏭

#### 👔 L1-7. 经理工作台 Manager Hub（角色过滤：仅经理可见）
- 为团队招人与入职 👔（编制申请、offer、入职任务）
- 管理我的团队 👔（岗位/薪酬变动、晋升、绩效案例）
- 团队考勤与休假 👔🏭（审批、排班）
- 处理团队问题 👔🔒（ER指导、工伤便利安排、纪律处理）
- 团队成员离职办理 👔

#### 🆘 L1-8. 帮助与联系HR Help & Contact HR
- 向HR提问（通用咨询——兜底安全网）
- 追踪我的请求

### 6.2 后台分层交付模型

| 层级 | 谁/什么 | 处理内容 | 目标占比 |
|---|---|---|---|
| **Tier 0** | 门户、知识库、AI虚拟助手、HCM自助 | 政策咨询、操作指引、状态查询、简单事务 | 60–75%拦截 |
| **Tier 1** | HR服务中心通才（区域中心、多语言、follow-the-sun） | 引导式事务、首触解决、分诊 | 20–30% |
| **Tier 2** | SSC专家团队（工资、福利、流动、入职运营） | 复杂事务、例外、供应商协同 | 5–10% |
| **Tier 3** | CoE专家与HRBP | 政策设计、ER调查 🔒、战略咨询 | <5% |
| **Tier 4** | 外部供应商、法务、劳资委员会 📍 | 外包履约、法律升级 | 例外驱动 |

> **关键原则**：层级对员工不可见。每个前台L3映射到一条履约路径（哪个Tier、哪个团队、哪个国家）——场景1（职能）与场景2（组织）以属性形式在此存续。

### 6.3 优劣势

| ✔ 优势 | ✘ 劣势与缓解 |
|---|---|
| 员工直观性最高——类目匹配人们描述需求的方式（"我要生孩子了"，而非"并行福利+法定休假事务"） | 服务可能同属两个类目（"育儿假"归休假还是家庭变化？）→ 用**多重归属**（一个户口+交叉链接）+ 强搜索缓解 |
| 经理工作台集中所有管人任务——经理满意度第一驱动因素 | 需要显性的流程与负责人映射层 → 初期设计更重（由SC-007/SC-018解决） |
| 人生事件旅程可编排跨职能打包（SC-021） | 旅程打包需要工作流编排能力（父案例+子任务） |
| 对HR重组和跨国运营差异有韧性（SC-017）；天然适配Tier 0拦截、chatbot与SSC成本度量 | |

## 7. 方案对比与推荐架构

### 7.1 对比矩阵

| 评估维度 | S1 职能 | S2 组织架构 | S3 SSC模式 |
|---|:---:|:---:|:---:|
| 员工直观性 | 🟡 中 | 🔴 低 | 🟢 高 |
| 经理体验 | 🔴 低（分散） | 🔴 低 | 🟢 高（经理工作台） |
| 路由/履约清晰度 | 🟢 高 | 🟢 高 | 🟡 中（需映射层） |
| 治理简单性 | 🟢 高（负责人=CoE） | 🟡 中 | 🟡 中（需旅程负责人） |
| HR重组韧性 | 🟢 高 | 🔴 极低 | 🟢 高 |
| 多国差异处理 | 🟡 中 | 🔴 低 | 🟢 高（L3范围化） |
| 跨职能人生事件 | 🔴 低（碎片化） | 🔴 低 | 🟢 高（旅程） |
| 流程架构对齐 | 🟢 高 | 🟡 中 | 🟡 中（经映射） |
| ServiceNow HRSD适配 | 🟢 高（COE模型） | 🟡 中（派单组） | 🟢 高（Employee Center主题+Journeys） |
| **🏭 一线员工适配（TE关键）** | 🟡 中 | 🔴 低 | 🟢 高（角色瓦片+My Time置顶） |

### 7.2 推荐目标架构："3 + 1 + 组织架构作元数据"

1. **前台 = 场景3**（8个生命周期/角色L1）用于员工门户、chatbot意图主题、知识浏览
2. **服务主数据骨架 = 场景1**（职能服务域）作为规范服务台账：每个L3有且仅有一个职能户口、一个全球服务负责人、一条流程映射（满足SC-006/013/020）
3. **组织架构 = 仅路由元数据**（场景2）：每个L3挂接国家/BU/站点/层级的派单组，可随时变更而不动导航
4. **一套共享分类主干**（L1/L2全球固定、L3治理化弹性）复用于服务目录、知识库、chatbot意图与报表（SC-009/011）

## 8. UX / IA / 导航 / 搜索

| 领域 | 问题 | 发现与建议 |
|---|---|---|
| **UX** | 员工如何搜索HR服务？ | 员工描述的是**症状和生活情境**，不是HR服务名——"工资单不对"、"要生孩子了"、"证明信怎么开"。典型入口占比：搜索框40–60%、通知直达链接约20%、类目浏览15–25%、chatbot持续增长。**🏭 工厂一线员工更依赖瓦片浏览而非搜索**（共用kiosk/手机打字摩擦大）→ 大图标L1瓦片+语音/扫码入口。**行动**：上线第一天即埋点搜索日志与零结果词——这是最便宜的持续分类校验工具 |
| **IA** | 什么类目名对员工直观？ | (1) 用员工词汇不用HR词汇——"Pay & Money"而非"Total Rewards"、"Time Off"而非"Absence Management"；(2) **卡片分类法**验证（开放式，每主要区域/角色30–50人，须含工厂员工），再**树测试**（任务式，首击成功率≥80%）；(3) 翻译后的标签单独测试——英文可行的名字在德语/中文里可能失效；(4) 禁用内部项目品牌名作类目；(5) L1不超过9个 |
| **导航** | 服务优先还是流程优先？ | **员工端服务优先（结果优先）**：员工要的是证明信、修正后的工资单、批准的假——不是"执行休假管理流程"。流程优先只适用于HR内部工作台。混合策略：暴露**旅程**（"我要搬迁"）在单一服务门面后编排多步流程。提供三条并行路径：搜索 / L1浏览 / 角色快捷入口（按角色和国家的Top 10任务，数据驱动季度刷新） |
| **搜索** | 搜索应否取代类目做路由？ | **是——搜索（及AI接入）应为主路由；类目是可浏览的安全网与发现层。** 要求：每国多语言同义词词典；容错拼写；结果排序知识（Tier 0）置于表单之上（拦截优先）；零结果告警工作流回灌分类治理；AI/虚拟助手意图模型训练于**同一套共享分类**（SC-009/011），保证chatbot、搜索、目录三者永不打架。类目仍必要：15–25%用户靠浏览、审计需要完整清单、新员工不知道该搜什么 |

## 9. 研究需求逐项响应（SC-005 ~ SC-029）

### 9.1 分类结构（SC-005 ~ 009）

| ID | 主题 | 建议方案 |
|---|---|---|
| **SC-005** | L1/L2/L3服务层级定义 | 采用§3.1三层模型：L1=8个生命周期域（前台），L2=每域4–8个服务组，L3=可发起服务项（挂负责人/SLA/受众/国家范围）。硬约束：L1≤9、每L1下L2≤8；需要第四层导航说明该L3应做成引导式表单而非类目 |
| **SC-006** | 企业级服务分类模型 | 四面向模型：每个L3携带 (1) 服务域（职能户口，场景1）、(2) 受众/角色、(3) 地域范围、(4) 交付属性（层级、渠道、履约组、SLA等级）。前台类目只是呈现映射；主键=全球唯一Service ID |
| **SC-007** | 流程-服务映射框架 | 多对多矩阵：全球HR流程模型（L1–L4）↔ 服务目录（L1–L3）。规则：每个L3映射≥1个流程；每个客户触发的流程变体映射到恰好1个规范服务；旅程映射到流程**捆绑包**。维护在服务台账中，不放在PPT里 |
| **SC-008** | 与全球HR流程架构对齐 | 职能骨架（场景1）锚定公司全球HR流程屋（若无则参考APQC"Develop and Manage Human Capital"）。每次分类发版跑对齐检查：无孤儿流程（面向客户的流程没有对应服务）、无孤儿服务（服务没有文档化流程） |
| **SC-009** | 知识分类 vs 服务分类 | **一套共享主干**：知识文章复用同一L1/L2，扩展知识专属面向（内容类型：政策/操作/FAQ/表单；适用国家；语言）。每个L3链接支持文章；每篇文章链接"升级服务"（"还需要帮助？→发起此请求"）。支撑拦截优先排序与一致的chatbot意图 |

### 9.2 分类治理（SC-010 ~ 012）

| ID | 主题 | 建议方案 |
|---|---|---|
| **SC-010** | 分类所有权治理 | 唯一责任主体：**全球HR服务管理办公室（HR-SMO）**拥有L1/L2与分类标准。跨职能**分类委员会**（HR-SMO主持+CoE代表+区域SSC负责人+HRIT+知识管理负责人）审批L1/L2变更；L3变更走轻量准入+HR-SMO签核。RACI公开；禁止"影子目录" |
| **SC-011** | 是否必须共享分类？ | **是——L1/L2在所有国家、BU和渠道强制统一**（门户、chatbot、知识、IVR、报表）。否则：全球报表失真、知识重复、chatbot意图不一致、跨国对标不可能。本地弹性仅授予L3（见SC-022–025） |
| **SC-012** | 未来分类治理模型 | 像运营产品一样运营分类：季度发版；变更准入表单（申请人、驱动因素、影响分析、涉及国家）；数据驱动评审输入（搜索零结果、错误路由率、季度请求<5次的目录项→合并/退役候选）；年度卡片分类/树测试复测；版本化分类资产+退役政策（退役类目做重定向，永不404） |

### 9.3 所有权与路由（SC-013 ~ 021）

| ID | 主题 | 建议方案 |
|---|---|---|
| **SC-013** | 服务负责人模型 | 每个L3有且仅有**一位全球服务负责人**（通常在职能CoE或全球流程负责人组织），对服务定义、全球模板、SLA、KPI、差异审批、持续改进负责。区域/国家**服务交付负责人**对本地履约绩效负责。负责人是台账中的结构化数据，不是文档 |
| **SC-014** | 案例负责人 vs 任务负责人 | **案例负责人**=端到端案例与全部员工沟通的唯一责任点；持有SLA时钟；永不"扔过墙"。**任务负责人**=履约离散子任务（如入职案例中的IT开通），有任务级SLA；对案例负责人汇报而非对员工。规则：员工永远只看到一个负责人 |
| **SC-015** | 路由框架 | 确定性路由矩阵，键=Service ID+员工国家+BU+**站点**🏭+员工群体（职员/一线/高管/外包）+语言+敏感标记 → 派单组+层级。优先级：(1) 保密覆盖（ER、高管薪酬→受限队列🔒），(2) 法定国家规则📍，(3) BU专属规则，(4) 全球默认路由。矩阵是受治理的配置数据，永不硬编码 |
| **SC-016** | 主归属规则 | 服务可能归属两个职能时的裁决顺序：(1) 谁拥有管辖该结果的**政策**；(2) 谁承担>50%履约工作量；(3) 谁拥有结果数据的记录系统；(4) 升级→分类委员会裁决并记录为先例。主负责人唯一且强制；次要团队以任务方式参与 |
| **SC-017** | 运营模式差异处理 | 维护**差异登记册**：同一L3服务、按国家的交付属性（履约方=SSC中心/属地HR/供应商；渠道；SLA）。员工可见的服务定义保持一致；仅履约路径不同。差异由全球服务负责人批准，过渡性差异设定时限（如"本地处理至2026年工资迁移到中心为止"） |
| **SC-018** | 服务拆解方法论 | 按**结果**拆解而非按团队。候选L3的通过标准：(a) 员工/经理会将其作为独立需求发起；(b) 有可定义的唯一负责人；(c) 有可度量的完成状态；(d) 请求量足以支撑独立表单/工作流（否则并入通用咨询+类目标签）。若某"服务"只作为另一服务的步骤存在，它是任务不是L3 |
| **SC-019** | 流程-任务所有权模型 | 每个多团队服务发布步骤级RACI：流程步骤→任务→归属团队→SLA→交接触发条件。所有权跟随任务，责任留在案例负责人（SC-014）。用案例转派次数指标季度复盘交接失败点 |
| **SC-020** | 消除重复服务定义 | (1) 唯一Service ID的规范**服务台账**为单一事实源；(2) 命名规范：`[结果动词]+[对象]（+受众）`，如"Request employment verification letter"；(3) 迁移时去重审计：按名称相似度+履约组+表单字段聚类，合并为规范项+国家范围（"在职证明-德国"+"在职证明-法国"→1项2国家变体）；(4) 新项准入含强制查重 |
| **SC-021** | 多团队工作流架构 | 父案例+子任务编排模式：人生事件旅程（入职、搬迁、离职）实例化一个父案例（员工可见的单一线程），派生跨HR职能、IT、设施、财务、供应商的并行/串行子任务。设计规则：依赖显式建模；子任务失败告警父案例负责人；员工状态视图聚合子任务进度；其他部门履约的跨部门任务使用企业级（非HR专属）任务类型 |

### 9.4 全球与本地（SC-022 ~ 025）

| ID | 主题 | 建议方案 |
|---|---|---|
| **SC-022** | 全球vs本地设计框架 | 三层模型：**全球核心**（L1/L2名称、服务定义、案例模型、KPI——固定）、**区域变体**（交付属性、语言、中心分配——受治理的弹性）、**本地法定**（仅存在于单一国家的L3，如中国住房公积金📍、德国劳资委员会协商📍、巴西FGTS📍、墨西哥PTU📍）。目标比例：按项数约80%全球/20%本地；度量并报告漂移 |
| **SC-023** | 国家差异治理 | 差异申请分级：**A类-法定/法律**（快速通道，需法律依据证据，全球服务负责人自动批准）；**B类-劳资委员会/工会协议**（附协议引用与到期跟踪后批准）；**C类-本地偏好**（"我们一直这么做"——需商业论证，默认答案是否）。所有差异入差异登记册并设复审日期 |
| **SC-024** | 全球模板策略 | 每个L3有**全球模板**：规范表单、工作流、知识文章骨架、SLA等级、KPI集。国家继承模板并以配置层方式套用已批准差异（永不fork副本）。模板版本化；按发布列车（如季度）推送并对本地化层做回归检查；**新国家/新收购公司接入=实例化模板+本地法定项**，典型建置以周计而非月计 |
| **SC-025** | 本地化方法论 | 四层本地化按序实施：(1) **语言**——标签、表单、知识、搜索同义词（专业翻译+在地评审）；(2) **法定合规**——必填字段、留存规则、同意书、劳资委员会可见性约束、数据驻留📍；(3) **文化/渠道**——中国的企业微信/钉钉使用习惯、德国的劳资委员会沟通、工厂的kiosk优先🏭；(4) **运营**——本地履约方映射、工时、节假日日历。每层有检查清单，国家HR负责人执行、全球服务负责人签核 |

| ID | 主题 | 建议方案与已知模式 |

| **SC-029** | 对比路由架构模式 | 观察到的模式：(a) **地域优先**（先路由到国家团队再按技能）——简单但损害中心规模经济；(b) **技能/服务优先+地点作属性**——最适合全球中心，推荐目标；(c) **层级式+升级机制**——通用基线；(d) **AI辅助接入路由**（自由文本分类到服务+路由）——增长最快，须以共享分类（SC-011）作为标签集；(e) **follow-the-sun队列**支撑24/7。建议：现在采用(b)+(c)，在干净分类之上试点(d) |

## 11. ★ TE专属针对性建议

### 11.1 一线员工优先（Frontline-First）——TE的第一设计原则 🏭

TE的员工主体在车间，多数无公司电脑和邮箱。**如果分类体系只在笔记本浏览器里好用，它对TE的大多数员工就是失败的。**

| 建议 | 具体做法 |
|---|---|
| **渠道策略** | 每个工厂部署自助kiosk（工牌感应登录）；手机端扫码直达（车间张贴二维码→高频服务）；中国工厂评估企业微信入口📍；无智能手机人群保留电话/现场HR窗口 |
| **工厂角色视图** | 一线员工登录看到的L1瓦片重排：**我的时间🏭 → 我的工资 → 休假 → 提出诉求 → 帮助**五大瓦片置顶放大；低频类目折叠。类目主干不变，只变呈现 |
| **主管代提单** | 产线主管/班组长可代表组员发起请求（换班、考勤更正、证明申请），员工通过短信/App收到确认——这是必备能力，不是增强项 |
| **语言按站点默认** | 分类标签按站点默认语言呈现（东莞=简中、华雷斯=西语、班贝克=德语），个人可切换 |
| **差异化KPI** | Tier 0拦截率分角色设定：办公人群目标65%+，工厂人群初期40–50%（现场HR窗口案例逐步线上化），避免"一刀切指标逼工厂关窗口"的体验灾难 |

### 11.2 事业部与站点维度处理

- **三大Segment/BU不做前台类目**——TE员工的HR需求（工资、休假、证明）与所属事业部基本无关；BU仅作HRBP路由与报表维度
- **对一线人群，"站点（Site）"是比BU更重要的路由键**：排班规则、工会协议、班车/食堂/宿舍类服务都挂在站点上。路由矩阵（SC-015）中站点维度权重应高于BU
- **例外**：确属BU专属的服务（如某事业部的销售激励咨询）通过受众范围控制可见性，不新建类目

### 11.3 三大本地化深水区

| 地区 | 关键事项 | 分类体系应对 |
|---|---|---|
| **中国** 📍 | 住房公积金、社保转移、离职证明法定时限、PIPL员工数据出境安全评估、企业微信生态 | 本地法定L3组（公积金提取/基数调整等）；数据隐私请求L3对接PIPL流程；**知识与案例数据的存储位置须在架构阶段与法务确认**——可能影响平台部署模式 |
| **德国/欧洲** 📍 | Betriebsrat对监控类数据的共同决定权、案例可见性限制、GDPR、协商前置 | ER与绩效类案例的字段级可见性控制🔒；涉及工时/行为数据的服务上线前走劳资委员会协商步骤（工作流内建）；**在设计阶段（而非上线前）就让德国劳资委员会参与**，避免整体延期 |
| **墨西哥** 📍 | Aguinaldo（年终金）、PTU（利润分享）、IMSS/INFONAVIT证明、工会集体合同 | 本地法定L3组；西语知识全量覆盖；工厂kiosk+主管代提单为主通道 |

### 11.4 分类体系 = 并购整合加速器

TE的持续收购意味着"新公司接入"本身应是一个**产品化场景**：

1. **收购整合手册**中加入"HR服务接入"标准包：Day 1开通"帮助与联系HR"+核心知识；90天内实例化全球模板+该国本地法定项；被收购公司存量HR联系方式重定向到统一门户
2. 差异登记册（SC-017/023）天然承接被收购公司的过渡期特殊政策（如"原公司福利保留至2026年"=带到期日的B/C类差异）
3. **度量**：新收购实体从交割到HR服务全量接入的周期，作为分类体系成熟度KPI（目标：≤90天）

### 11.5 组织变革与敏感场景

制造布局优化背景下，分类体系须预置：

- **保密路由队列** 🔒：涉及站点重组、集体协商、裁员支持的案例走受限可见性队列，仅授权ER/法务/指定HRBP可见
- **再就业支持服务组**（内部转岗优先推荐、技能重塑、离职过渡辅导）作为标准L3预置于"人生与工作事件→我要离职/退休"之下，需要时按站点快速激活
- 相关知识文章按站点+时间窗控制发布，避免全球可见引发不必要恐慌

### 11.6 技术落地建议（以WS0系统盘点结论为准）

- 若采用ServiceNow HRSD：前台8个L1映射为**Employee Center Topics**；场景1职能骨架映射为**COE配置**；人生事件旅程用**Lifecycle Events**实现；工厂kiosk评估Employee Center的kiosk/受限设备模式；虚拟助手意图集直接复用共享分类
- 与HCM（Workday/SuccessFactors等，待确认）的分工原则：**HCM做事务自助（Tier 0事务），服务平台做咨询、案例与编排**——员工端由统一门户屏蔽这一分工
- 工厂集成点：工牌系统（kiosk认证）、排班/MES系统（换班服务的数据源）、考勤系统（考勤更正闭环）
